# Adapters

The **proxy** is universal: every agent below configures stdio MCP servers with `command`/`args`/`env`,
so tool filtering works by pointing the server `command` at `toolgate-proxy` — no per-client code.

What needs an **adapter** is _server-level activation_: how the launcher applies "which servers are
active this session" and how it **restarts** the agent with a new set. Each CLI does that differently.

## Capability matrix

| Agent CLI              | MCP config             | Config location                               | How to apply the active set                                          | How to restart with a new set                | Defers tool schemas                  |
| :--------------------- | :--------------------- | :-------------------------------------------- | :------------------------------------------------------------------- | :------------------------------------------- | :----------------------------------- |
| Claude Code            | JSON `mcpServers`      | `.mcp.json` (+ settings)                      | `--settings` with `enabledMcpjsonServers` / `disabledMcpjsonServers` | relaunch `claude` via wrapper                | true (with tool search on)           |
| Codex CLI              | TOML `[mcp_servers.*]` | `~/.codex/config.toml` (or project `.codex/`) | `-c` runtime overrides, or `codex mcp add/remove`, or edit TOML      | relaunch `codex` with new `-c` / edited TOML | false                                |
| Antigravity CLI        | JSON `mcpServers`      | `mcp_config.json` (workspace/global)          | write the config file (file-driven; no launch flag)                  | relaunch after rewriting the file            | false                                |
| Karajan (orchestrator) | per-subagent           | injected per spawn                            | write a proxy/config profile per sub-agent before spawning           | orchestrator re-spawns sub-agents            | false (per-subagent, no tool search) |
| Generic MCP client     | `command`-based        | varies                                        | adapter-specific (or manual)                                         | client-specific                              | unknown                              |

> Sources for the config shapes are listed at the bottom.

## Per-agent notes

### Claude Code

- Proxy: in `.mcp.json`, set the server's `command` to `node`/the proxy binary and pass the real
  server via `TOOLGATE_UPSTREAM_*` env; `TOOLGATE_ALLOWED_TOOLS` reads the launcher-exported per-server value.
- Activation: the launcher computes the set and starts `claude --settings <tmp.json>` pinning
  `enabledMcpjsonServers`/`disabledMcpjsonServers` and forcing `enableAllProjectMcpServers:false`.
- Restart: relaunch through the wrapper; escalation via `extras`/`toolExtras` + `pendingRestart`.
- Caveat: if `.mcp.json` is generated by a sync tool, edit the **source**, not `.mcp.json`.

### Codex CLI

- Proxy: a `[mcp_servers.<name>]` block with `command`/`args` and an `[mcp_servers.<name>.env]`
  section carrying `TOOLGATE_UPSTREAM_*` + `TOOLGATE_ALLOWED_TOOLS`.
- Activation (`launchGating: "flagOverrides"`): Codex runs on the user's own `CODEX_HOME` (else `~/.codex`) and nothing is
  written. For each server that `config.toml` defines (toolgate recognises only `[mcp_servers.NAME]` headers, with a trailing comment, CRLF, spaces or a BOM allowed; `[[mcp_servers.NAME]]`, inline tables and dotted keys are not read, so those servers are left as configured), the launch passes `-c mcp_servers.<name>.enabled=false` when it is not
  active, or `-c mcp_servers.<name>.enabled_tools=[...]` when it is active and has a tool baseline. A `-c` for a server the
  config does not define breaks Codex's startup, so none is passed; Codex splits keys on dots, so a name with a dot (or any
  character outside letters, digits, `-` and `_`) cannot be addressed and is left as configured, with one note on stderr.
  Servers only in a project's `.codex/config.toml` are left as Codex loads them (it loads that file for a trusted project only).
  The user's own `-c` comes later and wins.
- Restart: relaunch `codex`; the overrides last for that launch only.
### Antigravity CLI

- Proxy: `mcpServers` entry with `command`/`args`/`env`, same JSON shape as Claude Code.
- Activation: file-driven — there is no launch flag to select servers. The adapter **writes**
  `mcp_config.json` for the computed set before starting the agent. The `buildConfigJson` function
  generates the file with only active servers, each pointing at `toolgate-proxy` with the allow list
  embedded in the server entry. No runtime env wrapper or proxy-side `configureProxy` call is needed
  — the proxy reads its allow list from env or its own config file at startup, which the adapter
  pre-populates. This is the _self-configured proxy_: tool filtering rides entirely on the written
  config, no launcher-side env injection at spawn time.
- Restart: rewrite the config file, then relaunch.
- Known caveat (2026): an env-var bug in the global MCP config has forced hardcoded keys for some
  users — verify before relying on `${VAR}` expansion in env values.

### Karajan (orchestrator)

- Karajan spawns multiple sub-agents; each is itself an MCP client. The win compounds: trimming every
  sub-agent's tool surface multiplies the savings by the number of agents.
- Integration: before spawning each sub-agent, the adapter writes a proxy config profile (or injects
  `TOOLGATE_UPSTREAM_*`/`TOOLGATE_ALLOWED_TOOLS`) scoped to that agent's task, so each agent only sees the tools its role
  needs. Bundling `toolgate-proxy` as a dependency is natural here.

## The adapter contract
Every adapter is a module registered in `packages/toolgate/src/adapters/index.js`. The registry
validates it when it is registered (modules) or first loaded (lazy loaders), and an invalid one fails
with its name and every field that breaks the contract. Contract tests
(`test/adapters/contract.test.js`) run over every registered adapter.

| Export                                | Contract                                                                    |
| :------------------------------------ | :-------------------------------------------------------------------------- |
| `capability`                          | frozen object, see below                                                    |
| `readServers(path)`                   | server names the agent has configured                                       |
| `definedServers({ cwd, homedir, env })` | optional: `{ name: { command, args, env } }`, the servers the agent's config defines for this launch (`{}` when none, or when absent); toolgate looks in them for the ones it can reveal tools of without a restart |
| `applyServers(active, …)`             | pure: what makes exactly the `active` set apply (settings, config text, env) |
| `installDiscovery({ cwd, template })` | where the Step 0 rule goes (`{ file, content }`), or `null` if `rules` is not `projectFile` |
| `buildToolEnv(config, state, active)` | env for the proxies                                                         |
| `launch(options)`                     | starts the agent, resolves `{ code, signal, … }`                            |
| `supportsResume`                      | boolean, equal to `capability.resume.supported === true`                    |

`launch` takes an options object (`launch({ prompt, … })`, the prompt form) or, for an adapter that
can be wrapped, `launch(args, { resume, raw, prompt, … })` with the agent's own arguments. Such an
adapter also exports `agentCli` (`bin`, `subcommands`, `valueFlags`, `booleanFlags`): how toolgate
reads, never rewrites, the agent's arguments. Claude Code is the first one.

## The wrapper: `toolgate <agent> [agent args…]`
```bash
alias claude='toolgate claude'
toolgate --no-route claude --model haiku -p "hi"   # toolgate flags go before the agent name
```
- Everything after the agent name is forwarded untouched, plus what the adapter generates (for
  Claude, `--settings <tmp>` pinning the active servers). An agent name is an adapter name or an
  alias (`claude` is `claude-code`).
- The agent's own subcommands (for Claude: `mcp`, `doctor`, `update`, … as listed by
  `claude --help`) are forwarded as they are (`toolgate claude doctor` is Claude's own; `toolgate doctor` is toolgate's): no settings are generated and no state is touched.
- The routing prompt is read only where it is unambiguous: the trailing argument counts when every
  flag before it has a known arity (`valueFlags`/`booleanFlags`); with an unknown flag in front, no
  prompt is taken and the baseline stays. Arguments are never rewritten, so skills are not appended
  to the prompt in this form.
- The exit code is the agent's (128 plus the signal number when a signal ended it), and SIGINT,
  SIGTERM and SIGHUP are forwarded while it runs.
- `resume`: `launch(args, { resume: true })` appends the adapter's resume argument (Claude:
  `--continue`) unless it is already there. The supervisor (#18) uses it.
- Supervisor: the agent cannot restart itself, so when the user ends the session and servers were
  escalated meanwhile, the wrapper relaunches it with the new active set and the resume argument, up
  to 3 times. The first message is not sent again. It does not relaunch when the adapter lacks
  `resume`, when the agent did not exit with 0, or in print mode (`agentCli.nonInteractive`, Claude's
  `-p`); then it prints the command to run. `toolgate need` (run by the agent) writes the same
  escalations and tells the agent how to restart: exiting the session when the adapter has `resume`,
  otherwise the exact `toolgate <agent>` command.
- A user `--settings` (a file or JSON, also as `--settings=`) is folded into the one toolgate generates.
  Claude honors only the last `--settings` and does not merge them (checked with the real CLI), so their
  keys are kept and the servers toolgate pins win.
- An adapter without `agentCli` answers "cannot be wrapped yet".

## Capabilities
A feature checks the capability instead of assuming Claude Code. A missing capability degrades the
feature and says what to do by hand; it never breaks the launch. Every field accepts `"unknown"`
(not verified) except `defersToolSchemas`; unknown is reported, never guessed.

| Capability           | Values                                                                              |
| :------------------- | :---------------------------------------------------------------------------------- |
| `rules`              | `{ kind: none \| projectFile (with path) \| launchInjection \| unknown, injectFlag? }`; `injectFlag` (e.g. `--append-system-prompt`) is the flag that passes the Step 0 text at launch when `client.injectRule` is on; `injectConfigKey` (e.g. `developer_instructions`) is the agent config key, set with `-c`, that takes the Step 0 text at launch (use one of the two) |
| `launchGating`       | `none`, `settingsFlag`, `configFile`, `flagOverrides`, `unknown`                    |
| `exclusiveMcpConfig` | boolean or `unknown`: the agent can load only the given servers                     |
| `resume`             | `{ supported: boolean \| unknown, arg }` (`arg` required when supported)            |
| `dynamicTools`       | boolean or `unknown`: honors `notifications/tools/list_changed`                     |
| `defersToolSchemas`  | boolean                                                                             |
| `commands`           | optional `{ kind: nativeDir \| none \| unknown, dialect, format: markdown \| toml, projectDirs, userDirs }`: where the agent keeps its own slash commands |
| `passthrough`        | `args` or `unknown`: how the agent's own arguments are forwarded                    |

### Commands

`commands` says where an agent keeps the slash commands of its own and how they are written. It is
optional (an adapter without it is still valid) and only describes the folders: toolgate indexes commands
as plain text and every agent that reads the Step 0 rule gets them on demand. It is used by
`toolgate commands import`, which reads the folders of the project (`--user`: of the home folder), and
by `toolgate doctor`. A folder that is a symlink, or that resolves outside the project or home folder, is
never read. The table lives in `src/adapters/commands.js`; `projectDirs` and `userDirs` are relative folders
(no absolute path, no `..`).

| Agent       | `kind`      | Project folders                                  | User folders                                         | Dialect       | Format   |
| :---------- | :---------- | :----------------------------------------------- | :--------------------------------------------------- | :------------ | :------- |
| Claude Code | `nativeDir` | `.claude/commands`                               | `~/.claude/commands`                                 | `claude`      | markdown |
| opencode    | `nativeDir` | `.opencode/command`, `.opencode/commands`        | `~/.config/opencode/command`, `.../commands`         | `opencode`    | markdown |
| Codex CLI   | `nativeDir` | none (user level only)                           | `~/.codex/prompts`                                   | `codex`       | markdown |
| Antigravity | `nativeDir` | `.agents/commands`, `.agents/workflows`          | none                                                 | `antigravity` | markdown |
| Karajan     | `none`      |                                                  |                                                      |               |          |
| generic     | `unknown`   |                                                  |                                                      |               |          |

The first folder of each list is where `toolgate commands bridge` writes the `/toolgate` command of that agent.

### Subagents

`subagents` says how an adapter registers the active subagents at launch (`src/adapters/subagents.js`): `launchFlag` passes them on the command line for that session only, `projectDir` writes marked files in a folder the agent reads and removes them afterwards, `none` and `unknown` register nothing (`toolgate need` then says the agent cannot register subagents).

| Agent       | `kind`       | Where                                   |
| :---------- | :----------- | :-------------------------------------- |
| Claude Code | `launchFlag` | `--agents <json>`                       |
| opencode    | `projectDir` | `.opencode/agents/` (`permission` starts with `"*": "deny"`, then allows what the subagent lists; the `<server>_*` key for a server it needs is not verified against opencode's documentation, and a wrong key can only deny) |
| Codex CLI, Antigravity, generic | `unknown` |                          |
| Karajan     | `none`       |                                         |

### Hooks and permissions

`hooks` and `permissions` say how an adapter applies the approved hooks and the permission units at launch (`src/adapters/applying.js`): `settingsFlag` puts them in the settings file of that launch (Claude Code's `--settings`, session-only, nothing written to the agent's own files), `configEnv` an inline config read from the environment (permissions only; opencode, through `OPENCODE_CONFIG_CONTENT`, which outranks the project config), `none` the agent has no such thing, `unknown` nothing is applied.

| Agent | `hooks` | `permissions` |
| :---- | :------ | :------------ |
| Claude Code | `settingsFlag` | `settingsFlag` |
| opencode | `none` (plugins are code with no trust step) | `configEnv` (`OPENCODE_CONFIG_CONTENT`; the mapping is partial and says what it cannot express) |
| Codex CLI, Antigravity, generic | `unknown` | `unknown` |
| Karajan | `none` | `none` |

`toolgate hooks status --effective` and `toolgate permissions status --effective` (add `--agent <name>`, `--json`, `--check`) print, per adapter, what the next launch passes: it reads the same plan the launch uses. A `none` or `unknown` adapter passes nothing (`unknown` means not verified) and `toolgate doctor` says so (`hooks.adapter`, `permissions.adapter`; an unapplied `deny` rule is an error). For opencode the output also lists the rules it cannot express (`permissions.unmapped` in doctor); a `deny` among them is marked `DENY NOT APPLIED`. `--check` exits 2 when a unit is held back or a deny/ask rule cannot be expressed.

### Tiers
Each tier includes the one before. `computeTier` and `whatWouldRaise` (`src/capability.js`) compute them.

1. **Skills on demand**: needs `rules` (`projectFile` or `launchInjection`).
2. **Servers on demand at launch**: needs `launchGating` other than `none`/`unknown`.
3. **Automatic restart**: needs `resume.supported`.
4. **Mid-session reveal**: needs `dynamicTools` plus the dynamic proxy.

### What each known agent declares today
| Agent       | `rules`                                 | `launchGating`  | `exclusiveMcpConfig` | `resume`               | `dynamicTools` | Tier |
| :---------- | :-------------------------------------- | :-------------- | :------------------- | :--------------------- | :------------- | :--- |
| Claude Code | `projectFile` `.claude/rules/toolgate-router.md` | `settingsFlag`  | true                 | `--continue`           | true           | 4    |
| Codex CLI   | `projectFile` `AGENTS.md`               | `flagOverrides` | unknown              | unknown                | unknown        | 2    |
| Antigravity | `projectFile` `.agents/rules/toolgate-router.md` | `configFile`    | unknown              | unknown                | unknown        | 2    |
| Karajan     | unknown                                 | `none`          | unknown              | unknown                | unknown        | 0    |
| opencode    | `projectFile` `AGENTS.md`               | `configFile` (`OPENCODE_CONFIG`) | unknown | unknown                | true           | 2    |
| generic     | unknown                                 | `configFile`    | unknown              | unknown                | unknown        | 0    |

Codex, Antigravity and opencode reach tier 2: each declares where the Step 0 rule goes and how a launch gates servers. What keeps
them from tier 3 is `resume`, which is `unknown` (not verified, not known to be missing). Karajan and `generic` are at tier 0 because
their rules location is `unknown`. `opencode` declares only what is known (`OPENCODE_CONFIG`, and `dynamicTools`, checked live
with opencode 1.18.4); `toolgate doctor` and `toolgate init` print each agent's tier and `whatWouldRaise` says what would raise it.

`generic` (`adapters/generic.js`) is driven by a spec, `{ bin, configFile, homeEnv, format: "json" | "toml",
serversKey | tablePrefix }`: toolgate writes `configFile` under a per-launch temp root, points `homeEnv`
at that root and spawns `bin`. `createGenericAdapter(spec)` returns a contract-valid adapter for an agent
with no dedicated one.

## Adding a new adapter
1. Confirm the client accepts `command`-based stdio servers, so the proxy works as-is.
2. Find how it selects active servers (launch flag, file or CLI subcommand) and declare it in
   `launchGating`; implement `applyServers`.
3. Find the config **source of truth** (beware generated artifacts) and implement `readServers`.
4. Declare every other capability, using `"unknown"` for what you have not verified.
5. Implement `launch`, register the adapter in `adapters/index.js` and run the contract tests.
6. Verify: the proxy trims a heavy server; escalation plus restart pulls a tool in; fail-open holds
   when no allow list is set.
